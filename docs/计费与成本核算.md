# 计费与成本核算手册

> 适用版本：**v1.6.5**（价格核对日期 2026-11-03）
>
> 读者：负责配单价、对账、做成本报表的管理员。界面操作见 [操作手册 3.4](操作手册.md#34-上游渠道)，数据落盘与接口见 [API 参考](API参考.md)。

---

## 1. 这套计价解决什么问题

不同厂商的账单不是「输入单价 × token + 输出单价 × token」这么简单：

| 厂商 | 计价特点 |
| --- | --- |
| DeepSeek | **峰谷分时**（工作日高峰 / 其余空闲，空闲约半价）+ 缓存命中价 |
| OpenAI | 输入 / 输出 + 缓存命中输入价（cached input，约输入价 1/10） |
| Anthropic | 输入 / 输出 + **缓存读**（约 0.1x）+ **缓存写**（约 1.25x） |
| Kimi | 输入 / 输出 + 缓存命中 + 缓存写入 |
| 通义千问 | **按单次输入长度分档**（0–256K / 256K–1M 不同价） |
| Gemini | 长上下文加价（Pro 超过 200K 后输入输出翻倍）——本质也是分档 |
| 豆包 | 输入长度三档阶梯（32K / 128K / 256K） |
| 智谱 | 固定输入 / 输出价（部分模型有缓存命中价） |

平台用一个统一的定价对象表达这些模式，记账时按**请求发生时刻**与**本次 token 构成**折算成元。

上表表达不了的部分（按次收费、代理商加价、按页计费）用**按模型 DIY** 的三个字段兜住：`perCall`（每次固定费）、`multiplier`（成本倍率）、`formula`（自定义公式）。每个模型可以各配各的，互不影响，详见 §3.5。

时间维度也一样：全局只有一套峰谷规则（§4），但每个模型可以带自己的**时段表** `periods`——时间段与对应价格都由这个模型自己定，详见 §3.6。

**范围说明**：这套计算只用于内部成本看板与部门核算，**不参与配额拦截**（配额按 token 计，不按钱计），也不参与上游路由。

## 2. 定价数据结构

存在 `data/db.json` 的 `pricing` 字段里，一个模型一条：

```json
{
  "deepseek-flash": {
    "in": 2,
    "out": 8,
    "cacheIn": 0.04,
    "idle": { "in": 1, "out": 4, "cacheIn": 0.02 }
  },
  "claude-haiku-5-5": {
    "in": 0.72, "out": 3.6, "cacheIn": 0.072, "cacheWrite": 0.9,
    "tiers": [
      { "upTo": 100000, "in": 0.72, "out": 3.6, "cacheIn": 0.072, "cacheWrite": 0.9 },
      { "upTo": 1000000, "in": 3.6, "out": 18, "cacheIn": 0.36, "cacheWrite": 4.5 }
    ]
  },
  "gpt-image-2": {
    "in": 18, "out": 72, "perCall": 0.35, "note": "按张计费 0.35 元 + token 费用"
  },
  "gpt-4o-mini-reseller": {
    "in": 1.08, "out": 4.32, "multiplier": 1.2, "note": "代理商加价 20%"
  },
  "legacy-ocr": {
    "in": 0, "out": 0, "formula": "prompt * 0.000002 + calls * 0.05", "note": "内部自建，按页计价"
  },
  "deepseek-flash-custom": {
    "in": 1, "out": 4,
    "periods": [
      { "name": "高峰", "days": [1,2,3,4,5], "windows": [["09:00","12:00"],["14:00","18:00"]], "in": 2, "out": 8 },
      { "name": "夜间特惠", "windows": [["23:00","07:00"]], "in": 0.5, "out": 2 },
      { "name": "双十一", "dates": ["2026-11-11"], "in": 0.3, "out": 1.2 }
    ],
    "note": "自带时段表，不依赖全局高峰规则"
  }
}
```

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `in` | ✅ | 输入（未命中缓存部分）单价，元 / 百万 tokens。高峰时段或不分时模型的默认价 |
| `out` | ✅ | 输出单价，元 / 百万 tokens |
| `cacheIn` | — | 缓存命中输入价。留空则按当前生效的输入价计 |
| `cacheWrite` | — | 缓存写入输入价（Anthropic / Kimi）。留空则按当前生效的输入价计 |
| `idle` | — | 空闲时段价，可含 `in` / `out` / `cacheIn` / `cacheWrite` 四个字段，各自独立生效；未配置 `idle` 的模型不分时。某字段留空时**沿用峰时的同名字段**，若峰时也没有则回落到「当前生效的输入价」 |
| `tiers` | — | 按输入长度分档，数组元素含 `upTo`（含该值的 tokens 上限）与 `in` / `out` / `cacheIn` / `cacheWrite`。**配置后优先于分时** |
| `periods` | — | **模型自定义时段**：数组，每段含 `name`、`days`（0–6，缺省=每天）、`windows`（`[["09:00","12:00"]]`，支持跨零点）、`dates`（`["YYYY-MM-DD"]`，当天整日生效）以及四个价格字段。自带时间规则，**优先于 `idle` 与全局高峰规则**，详见 §3.6 |
| `perCall` | — | 每次调用固定费用（**元**，不是百万 token 价）。按次计费的模型（图像、语音、检索）用它，叠加在 token 费用上 |
| `multiplier` | — | 成本倍率，对「(token 费用 + 按次费)」整体相乘。`1.2` 加价 20%、`0.8` 八折、`0` 内部免费。负数会被拒绝保存 |
| `formula` | — | 自定义金额公式（结果单位**元**），**替代**基础 token 费用。变量与语法见 §3.5；保存前校验，语法错误直接 400 |
| `note` | — | 备注，只用于界面展示（单价表模型名下方），不参与计算 |

单位统一为「**元 / 百万 tokens**」（`perCall`、`formula` 结果是**元**）；美元价按 `lib/preset-prices.js` 顶部 `USD_CNY`（默认 7.2）折算后写入。

## 3. 计算顺序与公式

### 3.1 顺序

```
1. 取基础价：in / out / cacheIn / cacheWrite
2. 若模型有 periods 且命中某一段 → 用该段的价格覆盖（自带时间规则，不再看全局峰谷）
   否则若模型有 idle 且请求时刻处于空闲时段 → 用 idle 里填了的字段覆盖
3. 若模型有 tiers → 按本次 promptTokens 选档，用档内填了的字段覆盖（覆盖前面两步的结果）
4. cacheIn / cacheWrite 仍为空 → 取当前生效的 in（空闲时段即 idle.in，否则基础 in）
5. 拆分 token：命中 / 写入 / 未命中
6. 求和 → token 费用
7. 若配了 formula → 用公式结果「替代」token 费用
8. 加上 perCall（每次调用固定费用）
9. 乘以 multiplier（成本倍率）
```

一句话：**分档优先于分时；分时内部，模型自定义时段优先于全局峰谷**。缓存价默认沿用峰时值，只有在 `idle` / `tiers` / `periods` 里显式写了 `cacheIn` / `cacheWrite` 才随时段变化——**DeepSeek 这类空闲缓存价极低的模型，必须显式填 `idle.cacheIn`（或写在对应时段的 `cacheIn`）**。

最后三步（公式 / 按次 / 倍率）是**按模型 DIY** 的钩子，不填就完全等价于旧版算法，见 §3.5。

### 3.2 token 拆分

上游返回的 usage 被归一化成四个计数：

| 字段 | 来源 |
| --- | --- |
| `promptTokens` | `prompt_tokens`（含缓存命中与写入部分） |
| `completionTokens` | `completion_tokens` |
| `cacheTokens` | DeepSeek `prompt_cache_hit_tokens`、OpenAI `prompt_tokens_details.cached_tokens`、Kimi 缓存命中 |
| `cacheWriteTokens` | Anthropic `cache_creation_input_tokens`、Kimi 缓存写入 |

```
hit   = min(cacheTokens, promptTokens)
write = min(cacheWriteTokens, promptTokens - hit)
miss  = promptTokens - hit - write
```

超出 `promptTokens` 的缓存计数会被裁剪（防止上游返回脏数据把成本算爆）。

#### 3.2.1 token 从哪来：优先上游，兜底才估算

| `usageSource` | 含义 | 与厂商账单的关系 |
| --- | --- | --- |
| `upstream` | 直接采信上游返回的 `usage` | 与厂商控制台同源，可逐条对上 |
| `estimated` | 上游没给 usage，网关按文本估算（CJK 1 token/字、其余 4 字符/token，且计入 `tools` 定义与 `tool_calls` 参数） | **只能参考**，agent 长上下文场景偏差可能超过一半 |

会落到 `estimated` 的典型情况：

1. **流式请求而上游没返回 usage**。OpenAI 兼容协议里流式默认不带 `usage`，必须请求 `stream_options.include_usage`。网关默认替客户端补上这个参数（设置项「流式请求向上游索取真实用量」= `settings.streamUsage`，默认开启），拿到后按真实值记账。
2. **自建代理不认 `stream_options`**。网关收到 400 且报错提到该参数时，会用客户端原始请求自动重试一次，不会因此报错；这类渠道的流式用量只能估算。

对账方法：在「调用日志」看「Token 来源」，筛出 `估算` 的记录——这些就是和厂商账单对不上的部分；确认设置里的开关已打开后，新请求应全部显示「上游返回」。

### 3.3 成本公式

分两段算：

```
第一段：token 费用
tokenCost = ( miss × 输入价
            + hit × 缓存命中价
            + write × 缓存写入价
            + completionTokens × 输出价 ) / 1,000,000

第二段：按模型 DIY 调整
amount  = formula ? 公式求值结果 : tokenCost     ← 公式配了就直接替代 tokenCost
总成本   = ( amount + perCall ) × multiplier      ← 没配时 perCall=0、multiplier=1
```

结果保留 8 位小数后累加，避免浮点误差滚雪球。

> 只配 `perCall` 不配公式，就是「token 费用 + 每次固定费」；只配 `multiplier`，就是整体打折/加价。两者都不配时 `总成本 = tokenCost`，与 v1.3.x 完全一致。

### 3.4 算例

**例 1：DeepSeek 空闲时段 + 缓存命中**

`deepseek-flash` 定价 `{ in: 2, out: 8, cacheIn: 0.04, idle: { in: 1, out: 4, cacheIn: 0.02 } }`，
某次请求 prompt = 10,000（命中 6,000），completion = 2,000，发生在周二 20:00（空闲）。

```
miss  = 4,000 → 4,000 × 1   = 4,000
hit   = 6,000 → 6,000 × 0.02 = 120
out   = 2,000 → 2,000 × 4   = 8,000
合计 12,120 / 1e6 = ¥0.01212
```

同一请求若发生在周三 10:00（高峰），用 `in/out/cacheIn`：`4,000×2 + 6,000×0.04 + 2,000×8 = 24,240 → ¥0.02424`，正好是空闲价的 2 倍。

**例 2：Anthropic 缓存写入**

`claude-sonnet-5-5`：`{ in: 14.4, out: 72, cacheIn: 0.72, cacheWrite: 18 }`，
prompt = 20,000（写入 10,000，命中 5,000），completion = 1,000。

```
miss  = 5,000  → ×14.4 = 72,000
write = 10,000 → ×18   = 180,000
hit   = 5,000  → ×0.72 = 3,600
out   = 1,000  → ×72   = 72,000
合计 327,600 / 1e6 = ¥0.3276
```

**例 3：分档（通义千问阶梯）**

`qwen3.7-plus`：`{ in: 2, out: 8, tiers: [{upTo: 262144, in: 2, out: 8}, {upTo: 1048576, in: 6, out: 24}] }`，
prompt = 300,000（超第一档），completion = 2,000。

```
选中第二档（≤1,048,576）：in=6, out=24
300,000×6 + 2,000×24 = 1,800,000 + 48,000 = 1,848,000 → ¥1.848
```

> 超出最后一档时回落到基础 `in` / `out` 计（相当于「超大输入按基础价」），如需更高价请自己再加一档。

### 3.5 按模型 DIY：按次、倍率与公式

三个字段互相独立、可任意组合，都只作用于**它所在的那一个模型**。界面上在「单价表 → 自定义 → 编辑」的单模型弹窗里配，也可以直接 `PUT /api/pricing`。

#### 3.5.1 什么时候用哪个

| 场景 | 怎么配 |
| --- | --- |
| 图像、语音、检索这类按次收费 | `perCall` = 每次单价（元）；token 费用照算，两者相加 |
| 代理商加价 / 内部结算折扣 / 免费额度 | `multiplier` = 1.2 / 0.8 / 0 |
| 厂商计价方式无法用 in/out/缓存/分档表达（按页、按秒、阶梯加保底） | `formula` |

#### 3.5.2 公式语法与变量

- 只支持数字、变量名、`+ - * /` 和括号；**不支持函数、幂运算（`**` 会直接报错）、百分号、中文符号**。
- 求值器是手写的 tokenizer + 递归下降解析（`lib/formula.js`），**不使用 `eval` / `new Function`**，不存在注入执行风险。
- 未知变量按 0 处理；除零返回 0——一条写坏的公式不会把整个记账流程炸掉。
- 变量表（价格类变量取「当前生效价」，即已含时段与分档覆盖后的值）：

| 变量 | 含义 | 单位 |
| --- | --- | --- |
| `prompt` | `promptTokens`（含缓存命中与写入部分） | tokens |
| `completion` | `completionTokens` | tokens |
| `cacheHit` | 缓存命中 tokens | tokens |
| `cacheWrite` | 缓存写入 tokens | tokens |
| `miss` | 未命中缓存的输入 tokens | tokens |
| `calls` | 调用次数，单次记账恒为 1 | 次 |
| `inPrice` / `outPrice` | 当前生效的输入 / 输出价 | 元 / 百万 tokens |
| `cacheInPrice` / `cacheWritePrice` | 当前生效的缓存命中 / 写入价 | 元 / 百万 tokens |
| `base` | 第一段算出来的 token 费用 | 元 |

- **保存时预编译校验**：`PUT /api/pricing` 先 `compile()` 一遍，语法错直接 400 并返回中文原因，避免「公式配上了却永远算不出钱」。
- **运行时兜底**：若公式意外失效（例如手改 `db.json` 写坏了），记账回落到 `base`，并在明细 `costDetail.formulaError` 里写明原因。

#### 3.5.3 算例：公式 + 按次 + 倍率

模型 `calc-model` 配 `{ in: 10, out: 40, formula: "base * 2 + 0.001", perCall: 0.002, multiplier: 2 }`，一次请求 prompt = 1,000、completion = 500：

```
第一段 tokenCost = (1,000 × 10 + 500 × 40) / 1e6 = 0.01 + 0.02 = 0.03
公式             = 0.03 × 2 + 0.001 = 0.061        ← 替代 tokenCost
加按次费         = 0.061 + 0.002 = 0.063
乘倍率           = 0.063 × 2 = 0.126
```

明细落盘 `costDetail = { base: 0.03, formula: 0.061, perCall: 0.002, multiplier: 2, prices: {...}, tokens: {...} }`，调用日志详情弹窗按这条链路逐行展示。

> 只用倍率（不配公式）时：`总成本 = (0.03 + 0.002) × 2`；只配按次（不配公式、倍率为 1）时：`总成本 = 0.03 + 0.002`。

#### 3.5.4 试算

单价弹窗的「试算」区（接口 `POST /api/pricing/test`）用**表单里还没保存的值**算一遍，不产生真实调用、不写日志，适合调公式时反复试。返回带 `nowPeak` / `nowIdle`，可确认分时是否按预期生效。

### 3.6 模型自定义时段（时间规则也按模型配）

分时到底怎么算、算哪个时间段、每段多少钱，**默认由每个模型自己决定**：`pricing[model].periods` 是一张时段表，时间与价格一起配。内置参考价里的 DeepSeek 已经预填好三段（工作日高峰 / 工作日其余时间 / 周末全天），开箱即用，不需要动任何全局开关。

§4 的 `settings.peak` 是一套**全局兜底**规则，v1.6 起**默认关闭**；它只在「模型填了 `idle`、却没配 `periods`」时才用得上，`periods` 一旦存在就完全接管这个模型的时间判断。

#### 3.6.1 结构

```json
{
  "in": 1, "out": 4,
  "periods": [
    { "name": "高峰",   "days": [1,2,3,4,5], "windows": [["09:00","12:00"],["14:00","18:00"]], "in": 2, "out": 8 },
    { "name": "夜间",   "windows": [["23:00","07:00"]], "in": 0.5, "out": 2, "cacheIn": 0.01 },
    { "name": "双十一", "dates": ["2026-11-11"], "in": 0.3, "out": 1.2 }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `name` | — | 标签，显示在调用日志的成本拆解里（缺省为「时段 N」） |
| `days` | — | 生效星期，0–6（0=周日）；缺省 = 每天 |
| `windows` | 二选一 | 时间窗数组，元素 `["HH:MM","HH:MM"]`；**支持跨零点**（`22:00-06:00`），结束写 `24:00` 表示到当天结束 |
| `dates` | 二选一 | 指定日期 `["YYYY-MM-DD"]`，**当天整日生效**，忽略 `days` / `windows` |
| `in` / `out` / `cacheIn` / `cacheWrite` | — | 该时段单价（元 / 百万 tokens），留空沿用基础价 |

`windows` 与 `dates` 至少要有一个，否则保存时返回 **400**；时间写法非法（如 `9-12`）同样 400。

#### 3.6.2 判定优先级

```
dates 段（整日） > 其余段按数组顺序先命中先用 > 都不命中则基础价
```

- 写日期的段**永远先判**，保证「大促/节假日特价」压得住常规时段，不用关心它在数组里的位置。
- 按星期的段**从上往下先命中先用**，所以更具体的段放前面（如「工作日 9-12 高峰」放在「每天 0-24 全天」之前）。
- 一个模型只要配了 `periods`，就**不再参考 `settings.peak` 与 `idle`**——两者是二选一的关系，`periods` 更具体、优先。
- `tiers`（按输入长度分档）仍然优先于所有时间维度：配了分档的模型，时段价只在档内没写的字段上生效。

#### 3.6.3 算例

模型配 `{ in: 10, out: 40, periods: [高峰(1-5, 9-12/14-18, in 20/out 80), 夜间(00:00-07:00, in 1/out 4), 双十一(dates, in 5/out 10)] }`，
一次请求 prompt = 1,000、completion = 500：

| 请求时刻（北京时间） | 命中 | 计算 | 结果 |
| --- | --- | --- | --- |
| 周二 10:30 | 高峰 | (1,000×20 + 500×80) / 1e6 | ¥0.06 |
| 周二 02:00 | 夜间 | (1,000×1 + 500×4) / 1e6 | ¥0.003 |
| 周二 13:00（12-14 空档） | 无 | (1,000×10 + 500×40) / 1e6 | ¥0.03 |
| 周六 10:30（星期不匹配） | 无 | 同上 | ¥0.03 |
| 2026-11-11 15:00 | 双十一 | (1,000×5 + 500×10) / 1e6 | ¥0.01 |

#### 3.6.4 怎么验证

单价弹窗的「试算」区有**试算时刻**（`POST /api/pricing/test` 的 `at`）：填一个目标时间（如周二 10:30），试算结果会明确写出命中哪一段；不填则按当前时间。试算不记账、不写日志，适合反复调时段。

#### 3.6.5 和 §4 全局规则的关系

| 场景 | 推荐做法 |
| --- | --- |
| 大多数模型都按 DeepSeek 官方峰谷 | 直接用内置参考价（DeepSeek 两个模型已带 `periods`），或照抄它的三段结构 |
| 个别模型分时规则不一样（夜市价、周末价） | 只给这个模型配 `periods`，别的模型不用管 |
| 大促当天全站特价 | 用 `periods` 的 `dates` 段（日期段优先，自动盖住常规段） |
| 想让某个模型不分时 | 删掉该模型的 `periods` 与 `idle`，只留基础价 |
| 老库里只填了 `idle` | 升级时会自动翻译成 `periods` 并关掉全局规则，见 §4.2 |

## 4. 全局高峰 / 空闲时段规则（默认关闭的兜底方案）

> v1.6 起这套规则**默认关闭**（`enabled: false`）。日常分时计价走 §3.6 的模型时段表；这里只在「模型填了 `idle`、但没配自定义时段」时才需要打开——打开后也只影响这一类模型，配了 `periods` 的模型始终以自己的时段表为准。

配置在 `settings.peak`（北京时间 UTC+8 判断，与服务器时区无关）：

```json
{
  "enabled": false,
  "days": [1, 2, 3, 4, 5],
  "windows": [["09:00", "12:00"], ["14:00", "18:00"]],
  "holidays": ["2026-10-01", "2026-10-02"]
}
```

判定逻辑：

```
若 !enabled                       → 非高峰（全按基础价）
若 北京日期 ∈ holidays            → 非高峰（节假日全天空闲）
若 星期 ∉ days                    → 非高峰（周末全天空闲）
若 当前时刻 ∈ 任一 windows        → 高峰
否则                              → 空闲
```

- `days` 用 0–6（0 = 周日）。
- 时间窗支持跨零点（如 `["22:00", "06:00"]`）。
- 这套默认值贴合 DeepSeek 官方口径；其他厂商如需分时，建议直接在模型时段表里配（§3.6），一致性更好、也不依赖全局开关。
- **是否分时由模型决定**：只有配了 `idle`（且未配 `periods`）的模型才用空闲价，其他模型在任何时段都按基础价。

### 4.1 法定节假日要人工维护

官方规则的「法定节假日」平台无法自动获取，需在高峰规则的节假日输入框里按年填（每年国务院公布后更新一次），格式 `YYYY-MM-DD`，逗号分隔；**更推荐写进模型时段表的 `dates` 段**——模型级的日期段优先于一切星期规则，也不用依赖全局开关。

### 4.2 从旧版升级：idle 自动翻译成 periods

v1.6 首次启动时（`store.load()` → `upgradeToModelPeriods`）做一次性迁移：

1. 把 `settings.peak.enabled` 置为 `false`（用 `settings.periodsMigrated` 标记，只执行一次，之后手动打开不会被再关掉）；
2. 对每个「有 `idle`、没有 `periods`」的模型，用旧的高峰规则生成一张等价时段表：

| 生成的段 | 时间 | 价格 |
| --- | --- | --- |
| `高峰` | 原 `days` + `windows` | 留空 = 跟随基础价（改基础价时自动同步） |
| `空闲` | 同一批星期，时间窗取高峰的补集（如 00:00-09:00 / 12:00-14:00 / 18:00-24:00） | `idle` 里填了的字段 |
| `空闲·非高峰日` | 其余星期，`00:00-24:00` | `idle` 里填了的字段 |
| `节假日` | 原 `holidays` 的日期（有才生成） | `idle` 里填了的字段 |

迁移前后**同一时刻的成本完全一致**；`note`、`formula`、`perCall`、`multiplier` 等其他字段原样保留。想回到旧行为：删掉模型的 `periods`，到单价页勾上「启用全局高峰时段」即可。

## 6. 常见核对问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 某模型成本恒为 0 | 单价表里没有该模型，或 `in`/`out` 都为 0 | 补单价；老用量不会重算 |
| 改了单价，历史成本没变 | 设计如此：成本在记账时按当时单价算好并落盘 | 需要重算就重置对应用量后重新产生；或导出日志自行按新价计算 |
| 空闲价没生效 | 全局高峰规则默认关闭（v1.6 起），只填 `idle` 不会分时 | 改用模型的「自定义时段价」，或在单价页勾上「启用全局高峰时段（兜底）」 |
| 分时完全没生效，全按基础价 | 模型既没配 `periods`，也没配 `idle`+全局规则 | 看单价卡标题右侧标签：「按模型时段计价 · N 个模型已配」 |
| DeepSeek 深夜还是峰时价 | 模型 `periods` 被删过，或段落顺序被改乱 | 重新「载入官方参考价」，或在弹窗里补回「空闲·工作日 / 空闲·周末」两段 |
| 自定义时段没生效 | ① 该时刻不在任何段内；② `days` 不含当天；③ 被更靠前的段先命中；④ 模型配了 `periods` 后全局峰谷本来就不参与 | 用「试算时刻」按目标时间验一次，结果里会写命中哪段 |
| 配了 `periods` 又配 `idle`，哪个生效 | `periods` 优先，`idle` 被忽略 | 二选一；想回全局规则就把 `periods` 删掉 |
| 保存时段报「时间窗无法识别」 | 写成了 `9-12` / `9:00~12:00` / 中文逗号之外的分隔符 | 统一写 `09:00-12:00`，多段用英文逗号分隔 |
| 分时价和分档价「打架」 | `tiers` 优先于 `idle`，配了 tiers 的模型永远按档走 | 一个模型只选一种模式 |
| 账单比平台算得高 | 漏了缓存写入、图片/音频等非 token 计费项、或厂商有最低消费 | 补齐 `cacheWrite`；非 token 项用 `perCall` / `formula` 补 |
| 账单比平台算得低 | 用错档位（超档回落基础价）、或汇率假设偏高 | 检查 `tiers.upTo` 边界、调整 `USD_CNY` |
| 美元价折算偏差 | `USD_CNY` 是固定常量，不随实时汇率变 | 按财务口径改常量后「载入官方参考价」重载 |
| 配了 `formula` 却仍按 token 算 | 公式运行时失效，已回落 `base` | 看明细 `costDetail.formulaError`；在单价弹窗重存一次让服务端预校验 |
| 按次费 / 倍率没生效 | 存成了 0/1，或被批量载入参考价覆盖 | `GET /api/pricing` 确认字段；参考价重载会覆盖同名模型，DIY 字段需重填（建议只对自定义模型名使用） |
| 成本正好是原价的整数倍 | 该模型配了 `multiplier` | 单价弹窗把「成本倍率」改回 1 |
| token 数和厂商官网对不上 | 该条日志的「Token 来源」是 `估算`：流式请求没拿到上游 usage，只能按文本长度估；agent 场景（大量工具定义）偏差最大 | 确认设置里「流式请求向上游索取真实用量」为开启；自建代理不支持 `stream_options` 时只能估算，属已知限制 |
| 流式请求的 token 明显偏小 | 同上；或上游把 `usage` 放在最后一个 chunk 而客户端提前断开（网关没读到） | 让客户端读到 `[DONE]`；必要时先切非流式做一次对照 |
| 缓存命中数与官网差很多 | 上游未返回 `prompt_cache_hit_tokens` / `cached_tokens`，或该次请求确实没命中缓存 | 看日志详情里「缓存命中」是否 > 0；冷启动首轮通常为 0 |

### 6.1 改汇率 / 更新参考价的流程

1. 编辑 `lib/preset-prices.js`：改 `USD_CNY`，或改模型价格，或仅把 `updatedAt` 改成新日期。
2. 重启服务，或在单价卡点「载入官方参考价」（等价于 `POST /api/pricing/presets`）。
3. 由于 `settings.presetsVersion !== updatedAt`，启动时会自动把新价补进未定价模型；同名模型是否覆盖取决于 `overwrite`（界面按钮默认覆盖）。
4. 同步更新本文档第 5 章的价格表与「核对日期」。
