# 计费与成本核算手册

> 适用版本：**v1.3.4**（价格核对日期 2026-11-03）
>
> 读者：负责配单价、对账、做成本报表的管理员。界面操作见 [操作手册 3.4](操作手册.md#34-上游渠道)，数据落盘与接口见 [API 参考](API参考.md)。

## 1. 这套计价解决什么问题

不同厂商的账单不是「输入单价 × token + 输出单价 × token」这么简单：

| 厂商 | 计价特点 |
| --- | --- |
| DeepSeek | **峰谷分时**（工作日高峰 / 其余空闲，空闲约半价）+ 缓存命中价 |
| OpenAI | 输入 / 输出 + 缓存命中输入价（cached input，约输入价 1/10） |
| Anthropic | 输入 / 输出 + **缓存读**（约 0.1x）+ **缓存写**（约 1.25x） |
| Kimi | 输入 / 输出 + 缓存命中 + 缓存写入 |
| 通义千问 | **按单次输入长度分档**（0–256K / 256K–1M 不同价） |
| Gemini | 长上下文加价（Pro 超过 200K 后输入输出翻倍）——本质也是分档 |
| 豆包 | 输入长度三档阶梯（32K / 128K / 256K） |
| 智谱 | 固定输入 / 输出价（部分模型有缓存命中价） |

平台用一个统一的定价对象表达这些模式，记账时按**请求发生时刻**与**本次 token 构成**折算成元。

**范围说明**：这套计算只用于内部成本看板与部门核算，**不参与配额拦截**（配额按 token 计，不按钱计），也不参与上游路由。

## 2. 定价数据结构

存在 `data/db.json` 的 `pricing` 字段里，一个模型一条：

```json
{
  "deepseek-flash": {
    "in": 2,
    "out": 8,
    "cacheIn": 0.04,
    "idle": { "in": 1, "out": 4, "cacheIn": 0.02 }
  },
  "claude-haiku-5-5": {
    "in": 0.72, "out": 3.6, "cacheIn": 0.072, "cacheWrite": 0.9,
    "tiers": [
      { "upTo": 100000, "in": 0.72, "out": 3.6, "cacheIn": 0.072, "cacheWrite": 0.9 },
      { "upTo": 1000000, "in": 3.6, "out": 18, "cacheIn": 0.36, "cacheWrite": 4.5 }
    ]
  }
}
```

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `in` | ✅ | 输入（未命中缓存部分）单价，元 / 百万 tokens。高峰时段或不分时模型的默认价 |
| `out` | ✅ | 输出单价，元 / 百万 tokens |
| `cacheIn` | — | 缓存命中输入价。留空则按当前生效的输入价计 |
| `cacheWrite` | — | 缓存写入输入价（Anthropic / Kimi）。留空则按当前生效的输入价计 |
| `idle` | — | 空闲时段价，可含 `in` / `out` / `cacheIn` / `cacheWrite` 四个字段，各自独立生效；未配置 `idle` 的模型不分时。某字段留空时**沿用峰时的同名字段**，若峰时也没有则回落到「当前生效的输入价」 |
| `tiers` | — | 按输入长度分档，数组元素含 `upTo`（含该值的 tokens 上限）与 `in` / `out` / `cacheIn` / `cacheWrite`。**配置后优先于分时** |

单位统一为「**元 / 百万 tokens**」；美元价按 `lib/preset-prices.js` 顶部 `USD_CNY`（默认 7.2）折算后写入。

## 3. 计算顺序与公式

### 3.1 顺序

```
1. 取基础价：in / out / cacheIn / cacheWrite
2. 若模型有 idle 且请求时刻处于空闲时段 → 用 idle 里填了的字段覆盖
3. 若模型有 tiers → 按本次 promptTokens 选档，用档内填了的字段覆盖（覆盖前面两步的结果）
4. cacheIn / cacheWrite 仍为空 → 取当前生效的 in（空闲时段即 idle.in，否则基础 in）
5. 拆分 token：命中 / 写入 / 未命中
6. 求和
```

一句话：**分档优先于分时**（现实中同一模型不会既分时又分档）。缓存价默认沿用峰时值，只有在 `idle` / `tiers` 里显式写了 `cacheIn` / `cacheWrite` 才随时段变化——**DeepSeek 这类空闲缓存价极低的模型，必须显式填 `idle.cacheIn`**。

### 3.2 token 拆分

上游返回的 usage 被归一化成四个计数：

| 字段 | 来源 |
| --- | --- |
| `promptTokens` | `prompt_tokens`（含缓存命中与写入部分） |
| `completionTokens` | `completion_tokens` |
| `cacheTokens` | DeepSeek `prompt_cache_hit_tokens`、OpenAI `prompt_tokens_details.cached_tokens`、Kimi 缓存命中 |
| `cacheWriteTokens` | Anthropic `cache_creation_input_tokens`、Kimi 缓存写入 |

```
hit   = min(cacheTokens, promptTokens)
write = min(cacheWriteTokens, promptTokens - hit)
miss  = promptTokens - hit - write
```

超出 `promptTokens` 的缓存计数会被裁剪（防止上游返回脏数据把成本算爆）。

### 3.3 成本公式

```
成本(元) = ( miss × 输入价
           + hit × 缓存命中价
           + write × 缓存写入价
           + completionTokens × 输出价 ) / 1,000,000
```

结果保留 8 位小数后累加，避免浮点误差滚雪球。

### 3.4 算例

**例 1：DeepSeek 空闲时段 + 缓存命中**

`deepseek-flash` 定价 `{ in: 2, out: 8, cacheIn: 0.04, idle: { in: 1, out: 4, cacheIn: 0.02 } }`，
某次请求 prompt = 10,000（命中 6,000），completion = 2,000，发生在周二 20:00（空闲）。

```
miss  = 4,000 → 4,000 × 1   = 4,000
hit   = 6,000 → 6,000 × 0.02 = 120
out   = 2,000 → 2,000 × 4   = 8,000
合计 12,120 / 1e6 = ¥0.01212
```

同一请求若发生在周三 10:00（高峰），用 `in/out/cacheIn`：`4,000×2 + 6,000×0.04 + 2,000×8 = 24,240 → ¥0.02424`，正好是空闲价的 2 倍。

**例 2：Anthropic 缓存写入**

`claude-sonnet-5-5`：`{ in: 14.4, out: 72, cacheIn: 0.72, cacheWrite: 18 }`，
prompt = 20,000（写入 10,000，命中 5,000），completion = 1,000。

```
miss  = 5,000  → ×14.4 = 72,000
write = 10,000 → ×18   = 180,000
hit   = 5,000  → ×0.72 = 3,600
out   = 1,000  → ×72   = 72,000
合计 327,600 / 1e6 = ¥0.3276
```

**例 3：分档（通义千问阶梯）**

`qwen3.7-plus`：`{ in: 2, out: 8, tiers: [{upTo: 262144, in: 2, out: 8}, {upTo: 1048576, in: 6, out: 24}] }`，
prompt = 300,000（超第一档），completion = 2,000。

```
选中第二档（≤1,048,576）：in=6, out=24
300,000×6 + 2,000×24 = 1,800,000 + 48,000 = 1,848,000 → ¥1.848
```

> 超出最后一档时回落到基础 `in` / `out` 计（相当于「超大输入按基础价」），如需更高价请自己再加一档。

## 4. 高峰 / 空闲时段规则

配置在 `settings.peak`（北京时间 UTC+8 判断，与服务器时区无关）：

```json
{
  "enabled": true,
  "days": [1, 2, 3, 4, 5],
  "windows": [["09:00", "12:00"], ["14:00", "18:00"]],
  "holidays": ["2026-10-01", "2026-10-02"]
}
```

判定逻辑：

```
若 !enabled                       → 非高峰（全按基础价）
若 北京日期 ∈ holidays            → 非高峰（节假日全天空闲）
若 星期 ∉ days                    → 非高峰（周末全天空闲）
若 当前时刻 ∈ 任一 windows        → 高峰
否则                              → 空闲
```

- `days` 用 0–6（0 = 周日）。
- 时间窗支持跨零点（如 `["22:00", "06:00"]`）。
- 这套默认值贴合 DeepSeek 官方口径；其他厂商如需分时，把对应模型填上 `idle` 即可复用同一套规则。
- **是否分时由模型决定**：只有配了 `idle` 的模型才用空闲价，其他模型在任何时段都按基础价。

### 4.1 法定节假日要人工维护

官方规则的「法定节假日」平台无法自动获取，需在单价表的节假日输入框里按年填（每年国务院公布后更新一次），格式 `YYYY-MM-DD`，逗号分隔。不填的后果是：节假日当天按工作日规则计，可能多算成本（不会少算）。

首次启动时自动补入「尚未定价」的模型；也可在单价卡点「载入官方参考价」重载（默认覆盖同名模型，自定义的其他模型不受影响），或调 `POST /api/pricing/presets` 按厂商选择性载入。

## 6. 常见核对问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 某模型成本恒为 0 | 单价表里没有该模型，或 `in`/`out` 都为 0 | 补单价；老用量不会重算 |
| 改了单价，历史成本没变 | 设计如此：成本在记账时按当时单价算好并落盘 | 需要重算就重置对应用量后重新产生；或导出日志自行按新价计算 |
| 空闲价没生效 | 模型没填 `idle`、高峰规则开关关闭、或当前确实处于高峰 | 看单价卡右上角徽标的当前时段；检查时间窗与节假日 |
| 分时价和分档价「打架」 | `tiers` 优先于 `idle`，配了 tiers 的模型永远按档走 | 一个模型只选一种模式 |
| 账单比平台算得高 | 漏了缓存写入、图片/音频等非 token 计费项、或厂商有最低消费 | 补齐 `cacheWrite`；非 token 项平台不计 |
| 账单比平台算得低 | 用错档位（超档回落基础价）、或汇率假设偏高 | 检查 `tiers.upTo` 边界、调整 `USD_CNY` |
| 美元价折算偏差 | `USD_CNY` 是固定常量，不随实时汇率变 | 按财务口径改常量后「载入官方参考价」重载 |

### 6.1 改汇率 / 更新参考价的流程

1. 编辑 `lib/preset-prices.js`：改 `USD_CNY`，或改模型价格，或仅把 `updatedAt` 改成新日期。
2. 重启服务，或在单价卡点「载入官方参考价」（等价于 `POST /api/pricing/presets`）。
3. 由于 `settings.presetsVersion !== updatedAt`，启动时会自动把新价补进未定价模型；同名模型是否覆盖取决于 `overwrite`（界面按钮默认覆盖）。
4. 同步更新本文档第 5 章的价格表与「核对日期」。
