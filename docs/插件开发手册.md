# 插件开发手册

> 适用版本：v1.1.0　|　代码位置：`lib/plugins.js`（约 320 行，建议先通读一遍再动手）
>
> 读完本手册，你可以把钉钉、LDAP、自建 HR 系统等任何「能给出人名/部门」的数据源接进平台。

---

## 1. 架构总览

```
管理台「扩展插件」页
   │  GET /api/plugins                 ← 列表（自动生成卡片）
   │  PUT  /api/plugins/:id/config     ← 保存配置
   │  POST /api/plugins/:id/test       ← 连接测试
   │  POST /api/plugins/:id/sync       ← 同步
   ▼
server.js（路由薄层，不含插件逻辑）
   ▼
lib/plugins.js
   ├─ REGISTRY：插件注册表（你要加的东西）
   ├─ 统一流程：读配置 → 调 fetchOrg → applyOrg 合并 → 记录同步结果
   └─ applyOrg：与平台数据的合并规则（所有插件共用，无需自己写）
```

分工很明确：**你只需要实现「怎么把外部数据拉下来」**，配置存储、表单渲染、合并入库、同步记录全由框架处理。

## 2. 插件契约

一个插件就是一个普通对象：

```js
{
  // 必填 —— 身份与展示
  id: 'dingtalk',                    // 唯一 ID，用于 URL（#/plugins/dingtalk）与配置存储
  name: '钉钉通讯录',                 // 卡片标题
  desc: '一句话说明用途与前置条件',    // 卡片与详情页描述
  fields: [ /* 表单字段声明，见 §3 */ ],

  // 必填 —— 唯一需要你实现的方法
  async fetchOrg(config, payload) {
    // config: 已保存 + 表单当前值合并后的配置对象
    // payload: sync 请求体透传（一般用不到，CSV 插件靠它收大文本）
    return {
      departments: [ { name: '研发部' }, { name: '市场部' } ],
      employees:   [ { name: '张三', email: 'z@corp.com', deptName: '研发部' } ],
    };
  },
}
```

写好后把它加进文件底部的 `REGISTRY` 数组即可，前端卡片、表单、按钮全部自动出现。

### 返回值要求

| 项 | 必填 | 说明 |
| --- | --- | --- |
| `departments[].name` | ✅ | 部门名，会按名称与平台合并 |
| `employees[].name` | ✅ | 员工姓名 |
| `employees[].email` | 建议 | 匹配已有员工的首要依据；没有也能同步（靠姓名匹配） |
| `employees[].deptName` | 建议 | 必须能对上 `departments` 里的某个 `name`，否则员工归到「未分配」 |

**不需要**返回额度、密钥、状态——这些是平台侧数据，同步永远不碰它们。

## 3. 配置表单字段（fields）

```js
fields: [
  { key: 'corpId', label: '企业 ID', type: 'text', placeholder: 'wwxxxxxxxx' },
  { key: 'appSecret', label: 'App Secret', type: 'password' },
  { key: 'apiBase', label: 'API 域名', type: 'text', placeholder: 'https://oapi.dingtalk.com',
    hint: '字段下方的灰色说明文字' },
  { key: 'text', label: '导入内容', type: 'textarea', placeholder: '每行一条…' },
]
```

- `type`：`text` | `password`（打码输入框）| `textarea`
- `key` 是配置对象的属性名，`fetchOrg` 收到的 `config` 就是 `{ corpId: '...', appSecret: '...' }`
- 配置随 `db.json` 持久化；「立即同步」会顺手保存表单当前值，不会丢

## 4. 合并规则（applyOrg，框架自动执行）

同步是**幂等**的，重复执行不产生重复数据：

1. **部门**按 `name` 精确匹配：已存在 → 完全不动；不存在 → 新建（额度全 0，状态启用）。
2. **员工**按 `email` 匹配 → 匹配不到再按 `name`：
   - 已存在 → 只更新 email 与归属部门，**额度、密钥、特例一概不动**；
   - 不存在 → 新建（自动签发 `sk-ai-*` 虚拟 Key）。
3. 同步结果（各计数 + 时间）记录到插件卡片上展示；「清空业务数据」会清掉这些记录但保留插件配置。

## 5. 错误处理约定

- **直接 `throw new Error('人话描述')`**：
  - 「连接测试」会把错误包成 `{ ok: false, message: e.message }` 显示在 toast 里；
  - 「立即同步」返回 HTTP 400 + 同样的 message。
- 必须处理的三类错误：凭证错误（把上游 errcode/msg 带上）、网络不通（框架的 `httpJson` 已带 15 秒超时并给出「请求超时」提示）、上游分页/权限问题。
- 参考：飞书插件对上游非 0 code 的处理 —— `throw new Error('拉取部门失败 [${j.code}]：${j.msg}')`。

## 6. 实战示例：接入钉钉

下面是一个可直接使用的完整插件（按钉钉新版 API `v2.0`）：

```js
const dingtalk = {
  id: 'dingtalk',
  name: '钉钉通讯录',
  desc: '用钉钉企业内部应用的凭证拉取部门与成员，需要「通讯录只读」权限。',
  fields: [
    { key: 'appKey', label: 'App Key', type: 'text' },
    { key: 'appSecret', label: 'App Secret', type: 'password' },
    { key: 'apiBase', label: 'API 域名', type: 'text', placeholder: 'https://oapi.dingtalk.com' },
  ],

  async token(cfg) {
    const base = trimBase(cfg.apiBase, 'https://oapi.dingtalk.com');
    const j = await httpJson(base + '/v1.0/oauth2/accessToken', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ appKey: cfg.appKey, appSecret: cfg.appSecret }),
    });
    if (!j.accessToken) throw new Error('获取 accessToken 失败：' + JSON.stringify(j));
    return { base, token: j.accessToken };
  },

  async fetchOrg(cfg) {
    const { base, token } = await this.token(cfg);
    const headers = { 'x-acs-dingtalk-access-token': token };

    // 1) 递归拉全部部门（从根 1 开始）
    const depts = [];
    let nextCursor = '';
    do {
      const j = await httpJson(base + '/v1.0/contact/departments?dept_id=1' +
        (nextCursor ? `&cursor=${nextCursor}` : '') + '&maxResults=100', { headers });
      for (const d of j.result?.list || []) depts.push({ id: d.deptId, name: d.name });
      nextCursor = j.result?.nextCursor || '';
    } while (nextCursor);
    const nameOf = new Map(depts.map((d) => [d.id, d.name]));

    // 2) 按部门拉成员
    const employees = [];
    for (const d of depts) {
      let offset = 0, size = 100;
      for (;;) {
        const j = await httpJson(
          `${base}/v1.0/contact/users?deptId=${d.id}&cursor=${offset}&maxResults=${size}`,
          { headers });
        for (const u of j.result?.list || []) {
          employees.push({ name: u.name, email: u.email || '', deptName: d.name });
        }
        if (!j.result?.hasMore) break;
        offset += size;
      }
    }
    return { departments: depts.map((d) => ({ name: d.name })), employees };
  },
};

// 注册：把 dingtalk 加进文件底部的数组
const REGISTRY = [feishu, wecom, csv, dingtalk];
```

完成后重启 `node server.js`，管理台「扩展插件」列表就会出现第四张卡片。

## 7. 开发与调试流程

1. 改 `lib/plugins.js`，`node --check lib/plugins.js` 过语法。
2. **用隔离实例调**，不要碰线上数据：
   ```bash
   GW_DATA_DIR=/tmp/gwtest PORT=8799 node server.js
   ```
3. 用 curl 快速验证（先 `POST /api/login` 拿令牌）：
   ```bash
   curl -s -X POST localhost:8799/api/plugins/dingtalk/test \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"config":{"appKey":"...","appSecret":"..."}}'
   ```
4. 调 `sync`，然后 `GET /api/employees`、`GET /api/departments` 核对结果；**再调一次 sync 确认没有产生重复**（幂等性）。
5. 回归：`node test/run.js`（39 项，与插件无关但确保没改坏公共代码）。
6. 测试完清理：`kill <PID>`（让它优雅退出落盘）+ `rm -rf /tmp/gwtest`。

## 8. 内置插件实现参考

| 插件 | 值得参考的点 | 位置 |
| --- | --- | --- |
| `feishu` | 分页 + 递归部门树；离职成员过滤（`status.resigned`）；ID→部门名映射 | `lib/plugins.js` 顶部 |
| `wecom` | 按 `parentid` 算部门深度，取成员**最深层**部门归属（避免挂在根部门） | 同上 |
| `csv` | 不需要网络：直接解析 `payload.config.text`，展示 fields 里的 textarea 用法 | 同上 |

## 9. 设计边界（什么时候不该做成插件）

- 只想**迁移一次**数据 → 用「文本 / CSV 导入」就够了，不用写插件。
- 需要**反向同步**（把平台用量推回 HR 系统）或**定时自动同步** → 当前框架只做手动触发的「拉入式」同步；需要时可在 `plugins.js` 加定时器并在插件上声明 `interval` 字段，属于框架层的扩展点。
- 需要**鉴权改造**（对接企业 SSO 登录管理台）→ 不属于插件体系，改 `server.js` 的 `/api/login`。
